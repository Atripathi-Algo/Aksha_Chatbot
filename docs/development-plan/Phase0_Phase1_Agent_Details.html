Phase 0 · Blocking

Platform foundation

None of the Phase 1 agents can run until these six pieces exist. They're infrastructure, not conversation logic — built once, used by every agent in every later phase.

0.1

Chatbot service scaffold

new service
What it does

Hosts the actual multi-agent runtime. This is the one new backend service everything else in the plan plugs into — separate from the existing Node API and Python image/report services.

How it works
  • A FastAPI app (aksha-chatbot-api) wraps a compiled LangGraph graph with nodes: authenticate_and_scope → load_checkpoint → normalize_query → route_request → domain_worker → verify_evidence → format_response.
  • Deployed as its own container, joining the existing aksha-net Docker network so it can reach node_backend and MongoDB directly.
  • Talks to the Node backend using a service-to-service credential, never a forwarded browser cookie.
Touches docker-compose.yml aksha-chatbot-api (new)
0.2

State & checkpointing

new database
What it does

Makes every conversation turn resumable and auditable — if the process restarts mid-answer, or an operator needs to review what the bot did six hours ago, this is the record.

How it works
  • A versioned ChatbotState Pydantic model carries thread_id, user_scope, extracted entities, tool results, and the final response status.
  • A LangGraph checkpointer writes to a new, separate MongoDB database (not the existing Aksha database) — collections chat_threads, chat_turns, chat_checkpoints.
  • A checkpoint is written before and after every tool call, and once more at the terminal state, keyed by (tenant_id, thread_id, turn_id, node_name, sequence).
Touches MongoDB (new db) ChatbotState schema
0.3

Router & formatter shells

core logic
What it does

Decides which single agent should answer a question, then turns that agent's raw findings into the sentence the user actually reads.

How it works
  • The router is itself a constrained model call: it must return one JSON object — {domain, agent, intent, entities, risk_level, needs_clarification, confidence} — never free text.
  • That JSON is schema-validated server-side before any tool is allowed to run; a malformed or out-of-catalog agent name is rejected, not guessed at.
  • The formatter receives only structured ToolResult and SourceRef objects and must cite them — it cannot introduce a fact that isn't already in the state.
Touches router.py (new) Output_formatter.py (new)
0.4

Typed tool registry

core logic
What it does

The only door between an agent and real data. No agent ever queries MongoDB, calls an internal service, or hits a filesystem path directly.

How it works
  • Each tool is registered with a Pydantic input/output schema, a domain, an access level (read / propose / write), required permission scopes, a timeout, and an idempotency flag.
  • An agent's LLM only ever sees the tool schemas registered to its domain — a Camera Operations call can't accidentally reach a Notification tool.
  • The server — never the model — injects tenant_id, site_ids, and requested_by into every call after argument validation.
Touches tool_registry.py (new)
0.5

JWT trust boundary

security
What it does

Establishes who is asking and what they're allowed to see — without standing up a second identity system.

How it works
  • Reuses the existing Aksha-jwt HS256 shared secret; verifies with jose.jwtVerify at the chatbot API boundary, mirroring the Node backend's jwtAuthMiddleware.
  • Fixes the issuer mismatch found in the audit: mobile tokens are signed with issuer mobile-app but verified against a hardcoded algosign — today, mobile tokens likely fail this check.
  • Because the token only carries siteId and a single role string, a small internal scope-resolution step maps those two fields to the permission set each tool actually needs, instead of waiting on new JWT claims.
Touches Aksha-jwt/middleware/validateJWT.ts scope_resolver.py (new)
0.6

Streaming & tracing

operability
What it does

Lets the user watch an answer appear live, and lets engineers see exactly what happened inside a turn afterward.

How it works
  • A Server-Sent Events endpoint streams the formatter's output token by token as it's generated.
  • Every node emits an OpenTelemetry span — chat.request → graph.run → router.invoke → worker.invoke → tool.call → formatter.invoke — tagged with thread id, a hashed tenant id, tool name, status, and latency.
  • Spans never carry raw prompts, JWTs, or RTSP URLs — only metadata about what ran and how long it took.
Touches SSE endpoint (new) OTel instrumentation
Phase 1 · Ship first

Green agents — zero backend change

Each of these seven only reads from APIs and files that already work today. The agent's job is to translate a natural-language question into a tool call and the tool result back into an answer — no new backend endpoint required.

1.1

Help & Product Guide Agent

read-only · no live data
Sample queries
How do I add a camera to a group?
What does the "Holiday Status" alert setting do?
Where can I find camera reports in the app?
What it does

Answers how-to and definitional questions about the Aksha product itself — it never touches an operator's alerts, cameras, or account.

How it works
  • Product documentation and the frontend's UserManual content are chunked and embedded into a FAISS index at build time.
  • A query runs hybrid keyword + vector search, retrieves the top 12 candidates, reranks to the top 5.
  • The formatter must cite the source document/section for every claim; no tenant filtering is needed since this content is global, not per-user data.
Reads indexed docs UserManual component content
1.2

Alert Investigation Agent (basic)

read-only
Sample queries
Show all high-risk alerts from Camera 12 today.
Why was alert A-1042 generated?
Were there any intrusion alerts on the warehouse camera yesterday?
What it does

Searches and explains individual triggered alerts within a bounded filter — camera, date, or alert type. Single-alert or simple-filter scope only in this phase; cross-alert correlation is a later phase.

How it works
  • The router extracts entities (camera name/id, alert type, date range) from the question.
  • A new search_alerts tool wraps the existing GET /api/alert/:camera_name and GET /api/recentAlert/:hours routes.
  • The server injects the caller's site-derived camera scope into the call — the model never sees or sets it.
  • Results come back as structured alert records (id, camera, timestamp, object class); the formatter turns them into prose that always cites the alert id.
Calls /api/alert/:camera_name /api/recentAlert/:hours
1.3

Camera Operations Agent

read-only
Sample queries
Which cameras have email alerts enabled?
Is Camera 23 live right now?
Show me all cameras configured for person detection.
What it does

Answers camera configuration and group-membership questions — status, priority, detection features, group assignment.

How it works
  • Calls get_camera / search_cameras / get_camera_group tools wrapping the existing GET /api/camera and GET /api/camgroup routes.
  • This is a near-direct pass-through: the tool adapter just maps schema fields (Priority, FPS, Feature[], Email_Alert) to plain-language labels for the formatter.
  • No new backend logic — the existing camera routes are already RESTful and well-shaped for this.
Calls /api/camera /api/camgroup
1.4

Live Monitoring Agent

read-only · time-sensitive
Sample queries
Is anything happening right now near the loading bay?
Which cameras currently have active alerts?
Show the current status of all camera groups.
What it does

Reports current operational state — which cameras are live, which have active alerts — as of the moment asked.

How it works
  • Reads GET /api/active/getLiveCamera and getSpotlightCamera, the same data the frontend's monitor view uses.
  • Optionally subscribes to the existing Socket.IO liveAllCamera event through a read-only adapter, rather than polling.
  • Because the backing data is a MongoDB change-stream snapshot rather than a guaranteed real-time push to the chatbot, every answer is labeled live, cached, or last-known-at-<timestamp> — never presented as certain when it might be stale.
Calls /api/active/getLiveCamera Socket.IO liveAllCamera
1.5

Insights & Analytics Agent

read-only
Sample queries
Which camera had the most alerts this month?
What are the busiest times of day for the entrance camera?
Compare this week's alert count with last week's.
What it does

Answers trend, count, and comparison questions over historical alert activity.

How it works
  • Calls the existing /api/insight and /api/insightReport routes, which read per-day JSON files (local disk or Azure Blob) produced by the Anomaly_model_training service.
  • A new tool adapter parses that JSON — total_alerts_generated, most_active_hour_for_each_object, peak_alert_time_hour — into a normalized structured-metrics object.
  • No new Mongo query is needed, but the adapter itself is new code: nothing today exposes this JSON in a shape an LLM tool call can consume directly.
Calls /api/insight /api/insightReport insight_report/{date}.json
1.6

Notification Agent (read)

read-only
Sample queries
Why didn't I receive an alert for Camera 7 this morning?
Which cameras have display notifications enabled?
Who is configured to receive alerts for the north gate group?
What it does

Explains notification configuration and history — who's set up to receive alerts and how, per camera or group.

How it works
  • Calls the existing /api/notification and camera-notification-manager GET routes.
  • Distinguishes a configured recipient (from the CameraNotificationManager schema) from confirmed delivery — the platform doesn't have full delivery-confirmation logs yet, so the agent must say "delivery confirmation isn't available" rather than imply an email was received.
Calls /api/notification /api/notification/group/:groupId
1.7

Multi-Language Support Agent

chatbot layer only
Sample queries
कैमरा 12 में आज कितने अलर्ट आए हैं? ― "How many alerts came from Camera 12 today?" (Hindi)
कैमेरा औफलाइन का अर्थ काय आहे? ― "What does camera offline mean?" (Marathi)
Same question asked in English, to confirm the response stays in the requester's language while alert IDs and timestamps stay canonical.
What it does

Lets an operator interact in their own language, without changing how any other agent works.

How it works
  • Not a domain worker with its own tools — it's a wrapper stage inside the formatter that translates only the final natural-language response.
  • Canonical fields (camera names, alert IDs, timestamps, URLs) stay in their original form so citations and downstream automation remain stable across languages.
  • Source language is detected from the incoming query or a client-supplied locale; internal tool calls and routing always run in English.
Touches Output_formatter.py
Delivery

How these seven agents reach the user

All seven share one delivery path on the frontend, adapted from a component that already exists in the investigation view.

What exists today

ChatPopover.tsx is a working dialog: message list with user/assistant bubbles, a text input with send-on-submit, local chat-history state, and a "download chat" action. It currently only talks to the image-analysis endpoint.

What changes for Phase 1
  • Generalize the popover so it isn't investigation-only, and point it at the new /api/chatbot/threads and /api/chatbot/threads/:threadId/messages routes.
  • Add source-citation rendering inside message bubbles, since every Phase 1 answer must carry a citation.
  • Add token-by-token rendering against the new SSE stream from Phase 0.
  • Surface a clarification question (e.g. "which camera did you mean?") as a visually distinct message type, not a plain assistant bubble.
