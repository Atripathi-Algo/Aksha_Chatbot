Aksha Support Chatbot · Rollout Plan

Ship the agents the backend already supports first

A phased build order for the multi-agent support chatbot, sequenced by how much of each domain worker's tooling already exists in the Aksha platform — not by feature importance.

Source design — CHATBOT_SYSTEM_ARCHITECTURE.md, SUPPORT_CHATBOT_AGENT_CATALOG.md Branch Chatbot_Abhishek Status Proposed sequencing
§

Every agent in the catalog is already labelled by backend readiness — green needs nothing new, orange needs a small response change, red needs new write paths and approval infrastructure. Building in that order means agent work is never blocked waiting on a backend team, and nothing that can mutate surveillance state ships before the approval & audit rails exist.

Phase 0

Platform foundation

blocking · no agents ship without this

The router, state graph, and trust boundary have to exist before any domain worker can be wired in. This is also where the audit uncovered problems that must be fixed before the chatbot can safely read production data.

Chatbot service scaffold

aksha-chatbot-api (FastAPI + LangGraph)

New deployable service, independent from the Node backend, per the service layout in the architecture doc.

State & checkpointing

chat_threads / chat_turns / chat_checkpoints

ChatbotState schema and MongoDB checkpoint store so turns are resumable and auditable.

Router & formatter shells

router.py · Output_formatter.py

Structured JSON route output; the model never gets a free-form agent name to return.

Typed tool registry

Pydantic input/output schemas

Allowlisted tool names and hosts — the model selects a tool, the server decides what it may touch.

JWT trust boundary

jose.jwtVerify, shared HS256 secret

Reuse the existing Aksha-jwt secret rather than issuing a second identity system.

Streaming & tracing

SSE + correlation IDs

Server-sent events for chat responses; OpenTelemetry spans per router/worker/tool call.

zero backend change

Phase 3

Red agents — deferred by design

major backend build · writes state

These either mutate surveillance state or need infrastructure the platform doesn't have yet — cross-camera correlation, async jobs, or an immutable audit trail. None of them should start until the preconditions on the right exist.

Must exist before any of these start

  • Approval-gate node with short-lived, argument-bound approval tokens
  • Idempotency keys on every write tool
  • chat_approvals and chat_audit_events collections
  • Role-based permission scopes actually enforced server-side
  • Unauthorized-action prevention proven at 100% on the security eval set
Cross-cutting

Risks the codebase audit surfaced

track alongside every phase

Found while mapping the platform ahead of this plan. None of these block Phase 1 outright, but each one limits how far a phase can safely go.

1

JWT scope is too thin to authorize per-tenant queries

Tokens carry only siteId and a single role string — no tenant_id, no roles array, no camera-level scope. Phase 0 needs a server-side scope-resolution step to compensate until richer claims exist.

2

Decoded JWT payload is never checked

The Node backend sets req.user from the token and stops there — no route filters data by role or site. Any read tool built on top of these routes inherits that gap until it's closed.

3

Mobile tokens likely fail verification

Mobile tokens are signed with issuer mobile-app, but the shared verifier hardcodes issuer algosign. Fix before the chatbot is exposed to mobile clients.

4

Live credentials are committed to the repository

client_secrets.json, credentials.json, plaintext RTSP camera credentials in rtsplinks.json, and default Mongo root credentials in docker-compose.yml all need rotation and exclusion from the chatbot's build context before it touches this data.

5

Insight and KPI data isn't in MongoDB

It's flat JSON on disk or in Azure Blob storage. Tools for the Insights, KPI, and Alert Summary agents need dedicated file/blob adapters rather than ordinary database queries.

Release gates

What "done" means per phase

Phase 0

Schema, permission, and checkpoint tests pass; JWT issuer bug fixed and scope-resolution verified.

Phase 1

All 7 agents live; tool-call validity ≥ 99% on the regression set; citation presence 100%.

Phase 2

Each new adapter covered by contract tests before its agent activates; no regression in Phase 1 agents.

Phase 3

Unauthorized-action prevention 100% on the security set; approval + audit flow tested in staging first.
